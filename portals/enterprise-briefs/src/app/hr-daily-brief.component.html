HR Daily Brief

Understand HR Brief — Azure Foundry Memory behavior

Overview Why many memory rows Foundry store settings App environment variables Populate & clear actions Scope & copy id Chat turn write policy Guidance

Overview

HR Daily Brief stores joiner records in MongoDB and preference facts in Azure Foundry Memory store hr-joiner-memory. Each joiner is isolated by scope = joiner_info_id (the UUID shown next to each list row).

Preference answers in chat come from Foundry Memory search hits for that scope—not from re-reading the left-hand joiner card on every reply.

Why many memory rows appear for one joiner

The app typically writes one profile update per joiner (food preferences, personal interests, and resume text). Because the store has User profile extraction enabled, Foundry’s chat model splits that text into several discrete user_profile facts—one row per fact in the Memories tab.

  • Same Scope on every row = same joiner.
  • Same timestamp usually means they came from a single populate / cold-miss seed.
  • This is expected Foundry behavior, not duplicate Mongo writes.

Splits help search return the relevant fact (for example food vs resume). More resume detail can produce more rows and slightly higher embedding cost.

Azure Foundry Memory store settings

On the store Details page, memory features are set at create time and cannot be changed in the portal afterward. Recreate the store (Clear Azure Foundry Memory, or middleware ensure) to change them.

Setting Effect
User profile When on, extracts many user_profile fact rows (the split).
User profile details Categories to extract. This project defaults to food preferences, personal interests, and resumes.
Chat summary Summarizes conversations into chat_summary items when enabled.
Procedural memory Learns reusable how-to / step knowledge when enabled.
Chat / embedding models Chat model drives extraction; embedding model powers search (text-embedding-3-small by default).

Middleware currently creates the store with user profile and chat summary enabled. Turning user profile off would stop multi-row splits but would also remove structured preference extraction unless storage/search logic changes.

The SDK also exposes create_memory to insert a single item by kind and scope if you ever need one row without extraction.

App environment variables

Configured in middleware .env (restart middleware after changes):

Variable Effect
HR_MEMORY_STORE_NAME Memory store name. Default hr-joiner-memory.
HR_MEMORY_PROFILE_DETAILS Text passed into Foundry user_profile_details. Narrower categories usually mean fewer extracted fact types.
HR_MEMORY_MAX_MEMORIES Cap on memory hits returned per chat search (default 5). Does not stop splitting on write.
HR_MEMORY_STORE_TURNS When true, may store compact Q&A turns after useful replies. Default false.
MODEL_DEPLOYMENT_NAME Chat deployment used by agents / memory chat model.
TEXT_EMBEDDING_MODEL_NAME Embedding deployment for memory search.

Populate & clear actions

  • Populate 1,000 joiners in MongoDB — generates/loads joiners into Mongo only. Does not seed Foundry Memory unless you also run the memory action.
  • Populate Azure Foundry Memory — writes preference profiles into Foundry for joiners already in Mongo (one update per joiner; Foundry may split into many facts).
  • Clear Azure Foundry Memory — deletes and recreates hr-joiner-memory. Mongo joiner rows are unchanged.

Local Docker volume wipes empty Mongo. Foundry Memory lives in Azure and must be cleared separately (button above or recreate the store).

Scope & copy id

The copy icon next to each joiner copies joiner_info_id. In Azure Foundry → Memory → hr-joiner-memory → Memories, set Scope = <copied value> to inspect that joiner’s facts only.

Chat turn write policy

  1. Search memory for the question (scope = joiner_info_id).
  2. On a cold miss (no hits), seed preferences from Mongo once, then search again. Existing hits are not re-written every turn.
  3. Call the HR agent with a slim joiner header when memory already has hits; fuller record on cold miss.
  4. Optional turn memory is off by default (HR_MEMORY_STORE_TURNS=false).

Guidance

  • Keep user-profile splits for preference / resume Q&A quality.
  • Keep turn writes off unless you need conversation recall.
  • To reduce fact volume: shorten resumes in the dataset, narrow HR_MEMORY_PROFILE_DETAILS, then clear and re-seed memory.
  • To stop splits entirely: recreate the store with user profile disabled (code change + clear), accepting less structured preference recall.
